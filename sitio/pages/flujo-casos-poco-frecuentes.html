6.1 Rechazo en stg

En principio no debería pasar, porque stg solo recibe lo que QA ya certificó. Cuando pasa, suele ser por una de estas causas:

  • Configuración distinta entre qa y stg: variables, certificados, URLs de servicios externos.
  • Integraciones reales: stg conversa con sistemas que en qa estaban simulados.
  • Datos parecidos a los de producción: volumen, casos raros, datos históricos.
  • Despliegue: scripts de base de datos o pasos manuales que fallan solo allí.
  • Prueba del cliente: DES-EST-016 §3 define stg como el ambiente de «pruebas funcionales con clientes internos y externos».

Qué hacer

  • Si la causa es configuración o infraestructura, se corrige el ambiente y no se toca git.
  • Si es código, se trata igual que un rechazo de QA: bug/az-<idBug>-<descripcion>-<ini> desde el último tag, tag patch, PR a sbx y recorrido completo qa → stg → prod. La corrección vuelve a pasar por QA (PoC 7a).

Este caso no tiene diagrama propio

El flujo es el del diagrama de Defecto, con el rechazo en stg en lugar de qa: ver Defecto (QA rechaza una versión).

Reglas que aplica: R2 R5 R6

6.2 Versión certificada que espera al cliente mientras otra debe salir (retiro temporal)

Situación: QA certificó A (v1.6.0) y solo falta la aprobación del cliente, que tarda. Mientras tanto se termina B. A no debe salir a producción sin aprobación.

Cómo funciona con la regla de cadena

  1. A se queda en qa (R8).
  2. B, antes de su tag, incorpora el último tag. Así v1.7.0 = A + B, y sube a qa sin mezclas.
  3. Si el cliente aprueba A antes de que B deba salir, todo sigue normal.
  4. Si B debe salir y A sigue sin aprobación, se hace un retiro temporal de A: una rama nueva, con el ID de un ítem nuevo, desde v1.7.0; git revert del commit de A y el tag v1.7.1. Luego PR a sbx y recorrido qa → stg → prod. QA prueba B sin A.
  5. Cuando el cliente aprueba A, se revierte el retiro (el «revert del revert») en otra rama nueva desde v1.7.1, con el tag v1.8.0. Luego PR a sbx y qa → stg → prod.

En ningún paso llega A a stg ni a prod sin aprobación.

¿Se cuela lo no aprobado?

A producción, no. A viaja dentro de las versiones de qa, pero solo sube a stg y prod con aprobación, o retirado con el revert. La PoC lo probó en el escenario 12 (I1–I7 ✔ en los dos modos): v1.7.1, la versión sin A, llegó a prod sin A, y A apareció en prod solo con la reintroducción.

Re-pruebas: QA vuelve a probar dos veces

QA tiene que volver a probar la versión sin A, y otra vez cuando A regresa.

Base de datos: el revert de git no la deshace

Si A incluía cambios de base de datos, el revert de git no los deshace en la base. Hay que preparar un script de reversión.

Conflicto en el revert

Si B modificó el mismo código que A, el revert puede tener conflicto. Se resuelve en la rama del retiro.

Recuperar A volviendo a hacer merge de su rama

Para recuperar A no sirve volver a hacer merge de su rama original: git responde «Already up to date» y no hace nada (PoC 8). Siempre es «revert del revert».

Si esto pasa seguido

La solución de fondo no es de ramas sino de código: interruptores de funcionalidad (feature flags). A sale a producción apagada y se enciende cuando el cliente aprueba. Requiere esfuerzo de desarrollo, pero elimina los retiros.

Reglas que aplica: R2 R3 R6 R8 R9

6.3 Entrega parcial (salen A y C, pero no B)

Es el mismo mecanismo que 6.2: sobre el último tag (A+B+C) se hace un retiro temporal de B y se crea el tag (A+C). Ya no hace falta una «rama de integración» sin nombre en el estándar (PoC 5c).

Este caso no tiene diagrama propio

El flujo es el del diagrama de 6.2: el retiro de B ocupa el lugar del retiro de A.

Reglas que aplica: R2 R9

6.4 Requerimiento cancelado definitivamente

Rama con el ID de un ítem nuevo («retirar HU 801»; no se reutiliza el nombre de la HU cancelada), git revert, tag patch, PR y recorrido normal. Si algún día se pide de nuevo, se hace un revert del revert (PoC 8).

Este caso no tiene diagrama propio

El flujo es el del diagrama de 6.2 hasta el retiro (v1.7.1), sin la reintroducción.

Reglas que aplica: R6 R9

6.5 Rollback de producción

No se puede promover un tag anterior

Git ve que prod ya lo contiene y no cambia nada; el PR «se completa» pero prod sigue igual (PoC 9a). El rollback se hace en dos capas.

  1. Inmediato (operación): se redespliega desde el pipeline el artefacto del tag anterior (por ejemplo v1.3.0), sin tocar git. Durante ese rato, la rama prod dice v1.4.0 aunque lo desplegado sea v1.3.0; se deja anotado en el ticket GLPI.
  2. Regularización (git): se trata como un hotfix cuya corrección es el revert (ver Incidencia urgente: hotfix). Aquí v1.4.0 es la cabeza de la cadena y qa tiene lo mismo que prod (nada en pruebas), así que el recorrido es el normal, con el PR a sbx primero: sbx → qa → stg → prod. Si qa tuviera otra versión en pruebas, sería como en el hotfix: stg → prod, re-etiquetar la cabeza, PR a sbx y promover el tag re-etiquetado a qa. La PoC comprobó que el contenido del tag nuevo queda idéntico al de v1.3.0 (9b).

El rollback no «vuelve atrás» en git: avanza con una versión nueva que deshace la anterior. Como v1.4.0 era la cabeza de la cadena, no hay que re-etiquetar nada.

Base de datos: el revert de git no la deshace

Los cambios de base de datos de v1.4.0 no se revierten con git. Toda entrega con migraciones debe traer su script de reversión.

Reglas que aplica: R2 R5 R6 R7

6.6 Conflicto entre dos requerimientos

Dos HU cambian las mismas líneas. La primera en crear su tag pasa sin problema. La segunda encuentra el conflicto al aplicar la regla de cadena (paso 3 del flujo de Requerimiento), en su propia rama, y lo resuelve allí.

El conflicto se resuelve en la rama, nunca en sbx

sbx nunca recibe una resolución directa (PoC 6).

Reglas que aplica: R3 R5

6.7 Dos tags al mismo tiempo

Si dos personas crean un tag casi a la vez desde la misma cabeza, el segundo tag no contiene al primero y la cadena se rompe. Al promoverlo, el PR se bloquea o mezcla.

En el diagrama, v1.7.0 se creó sin contener a v1.6.0, así que la cadena se rompe. La validación automática rechaza el PR con CADENA. La rama incorpora v1.6.0, crea v1.7.1 declarando Descarta: v1.7.0, y ese es el tag que sigue adelante.

Prevención

Que el tag lo cree el líder técnico justo antes de completar el PR (R4), más la validación automática de la sección 7 de la guía.

Si ya pasó: el segundo tag no se usa

El segundo tag no se usa (R10). Se incorpora el primero en la rama y se crea un tag nuevo, cuyo mensaje lleva la línea Descarta: <tag que no se usa>. La validación automática rechaza el PR del segundo tag con CADENA y explica cómo hacerlo (PoC, grupo G2).

Reglas que aplica: R3 R4 R10

6.8 Hotfix cuando stg no está igual a prod

No probado en la PoC

Este caso no se probó en la PoC.

Si se cumple R8, solo pasa durante la ventana de un paso a producción. Las opciones:

  • (a) Si la versión que está en stg ya tiene aprobación, se termina su paso a prod. El hotfix se hace después, sobre el nuevo tag de prod.
  • (b) Si no tiene aprobación, no hay ambiente libre para validar el hotfix sin mezclar. Se escala al comité de cambios.

Este caso no tiene diagrama propio

El hotfix en sí es el de Incidencia urgente: hotfix.

Reglas que aplica: R7 R8

6.9 Segundo hotfix sobre la misma versión

Prod tiene v1.4.0.1 y aparece otra urgencia. La rama es hotfix/glpi-<ticket>-<descripcion>-<ini>, desde v1.4.0.1, y el tag es v1.4.0.2. El resto, igual que en el hotfix.

Este caso no tiene diagrama propio

Es el mismo diagrama de Incidencia urgente: hotfix, partiendo de v1.4.0.1 en lugar de v1.4.0.

Reglas que aplica: R2 R7

6.10 Fallo de ambiente que no es de código

Si lo que falla es configuración, credenciales o infraestructura, no se crea ninguna rama ni tag. Se corrige el ambiente y se registra en el ticket.

6.11 Pruebas automatizadas

Una rama por cada prueba automatizada sobre un componente (DES-EST-016 §4.5): test/az-<id>-<desk|web|serv>-<descripcion>-<ini>, donde <id> es el requerimiento o ticket que origina la prueba.

Sigue el mismo flujo de Requerimiento hasta el PR a sbx: nace del último tag, aplica la regla de cadena, se etiqueta antes del PR y el tag sube el patch, porque no cambia la funcionalidad. ARQ-PRO-001 §8 termina en el merge a sbx: el tag queda en la cadena y viaja con la siguiente promoción, sin promoverse por separado.

Qué probó la PoC

La PoC probó el nombre y el paso a sbx (escenario 12 con -Nomenclatura carpetas).

Reglas que aplica: R2 R3 R4 R5
