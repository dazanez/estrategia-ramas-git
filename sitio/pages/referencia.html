Reglas R1–R11

Las reglas generales de la estrategia. Cada flujo y cada receta enlazan aquí a las que aplican.

#ReglaPor qué
R1sbx, qa, stg y prod están protegidas: sin push directo, todo entra por PR con revisión. La única excepción es el commit inicial al crear el repositorio.Trazabilidad y revisión obligatoria (ARQ-PRO-001 §5).
R2Toda rama de trabajo nace de un tag: git checkout tags/<tag> -b <rama>. El hotfix nace del tag de producción; todo lo demás, de la cabeza de la cadena.Así nunca se arrastra código que no pertenece a ninguna versión (PoC 3 y 4).
R3Regla de cadena. Antes de crear el tag, la rama incorpora el último tag (git merge <último tag>). Si hay conflicto, se resuelve en la rama de trabajo.Mantiene una sola cadena y evita mezclas en los ambientes (PoC 5b, 12).
R4El tag se crea en la rama de trabajo, antes de completar el PR a sbx. Lo crea o lo valida el líder técnico (DES-EST-016 §4.1). Siempre es un tag anotado (git tag -a ... -m).La versión contiene solo lo que se probó (PoC 3b y 4b frente a 3a y 4a).
R5PR de la rama de trabajo a sbx. Con R2–R4, sbx queda siempre con el mismo contenido que el último tag.sbx deja de tener "cosas sueltas" sin versión (PoC 12).
R6La promoción siempre parte de un tag, con promote/<tag>-to-<ambiente>, en orden qa → stg → prod. prod solo recibe desde stg. La rama promote/ se borra al terminar.DES-EST-016 §4.12 y ARQ-PRO-001 §6.7–6.11.
R7La única excepción al orden es el hotfix, que entra directo a stg (salta qa).qa suele tener otra versión en pruebas que no debe mezclarse (PoC 2).
R8stg solo recibe versiones aprobadas para salir a producción en esa ventana. Lo que espera la aprobación del cliente se queda en qa. Así stg es casi siempre igual a prod y sirve para validar hotfixes.Sin esto, un hotfix no tendría dónde validarse (sección 6.8).
R9Nombres únicos: una rama o un tag nunca se reutilizan. Cada iteración, retiro o reintroducción usa el ID de un ítem nuevo.DES-EST-016 §4.10 y §4.12 (PoC 4, 9a).
R10Los tags nunca se mueven ni se borran. Un tag creado por error queda sin usar y se declara en el mensaje del siguiente tag con una línea Descarta: <tag> (motivo). Así la validación automática sabe que no forma parte de la cadena.Un tag es el registro de lo entregado.
R11Tipo de merge en Azure DevOps: solo "Basic merge (no fast-forward)". Squash y rebase quedan prohibidos.Ver sección 7.

Reglas de escritura

  • Todo en minúsculas, incluidas las iniciales. En Windows, git no distingue mayúsculas en las carpetas. En la PoC, con una carpeta Bug/ existente, la rama bug/az-2-y-dd se creó como Bug/az-2-y-dd sin avisar, y su git push falló.
  • Solo letras sin tilde, números y guiones: sin espacios, tildes ni ñ (validacion, contrasena). Git acepta tildes, pero no todas las herramientas (pipelines, consolas, URLs) las manejan bien. Es la misma regla que DES-EST-016 §4.4.3 pone a los nombres de componentes.
  • Descripción corta: de 2 a 5 palabras, sin conectores ni preposiciones ("de", "para", "entre"; DES-EST-016 §4.4.3). El nombre completo no pasa de 60 caracteres: los nombres muy largos dependen de que cada equipo tenga core.longpaths activado.
  • El sistema va siempre, también en feature y test. Azure DevOps y GLPI numeran por separado y el mismo número puede existir en los dos. Además, un requerimiento que llegue por GLPI se nombra igual (feature/glpi-…), sin crear una regla aparte.
  • Nunca crear una rama llamada solo feature, bug, hotfix, test o promote. Git no permite que un nombre sea a la vez rama y carpeta: si existe la rama hotfix, nadie puede crear hotfix/... (comprobado en la PoC).
  • No se incluye el sprint. El sprint está en Azure Boards y queda obsoleto si la HU pasa a otro sprint; el ID es único.
  • No se incluye la versión base en el hotfix. El tag del hotfix ya la dice: v1.4.0.1 es una corrección sobre v1.4.0.

Comprobación automática

Un nombre es válido si cumple una de estas dos expresiones y no pasa de 60 caracteres. Son las que usa la PoC (I4) y las que usaría la validación de Azure DevOps (sección 7):

^(feature|bug|hotfix)/(az|glpi)-[0-9]+(-[a-z0-9]+)+-[a-z]{2,3}$
^test/(az|glpi)-[0-9]+-(desk|web|serv)(-[a-z0-9]+)+-[a-z]{2,3}$

Validador

Escriba o pegue el nombre de una rama. Se valida con las dos expresiones de arriba y el límite de 60 caracteres, y si falla se explica qué parte falla.

Transición: las ramas abiertas con el formato anterior (HU_…, BUG_…, AUT_…) terminan con ese nombre; las nuevas usan este.

Configuración de Azure DevOps

Propuesta — no probada en Azure

La PoC simuló Azure DevOps con git local. Lo que sigue hay que configurarlo y probarlo en el proyecto real; los nombres de las opciones pueden variar según la versión de Azure DevOps.

El paso a paso, con el plan de pruebas, está en CONFIGURAR-AZURE-DEVOPS.md.

La validación automática

La validación automática ya está escrita y probada en la PoC:

  • ci\Validar-PR.ps1 es el script.
  • ci\azure-pipelines-validar-pr.yml es el pipeline que lo ejecuta en Azure.
  • probar-validar-pr.ps1 es la prueba: 48 casos sobre un remoto local que simula Azure, con el resultado esperado en todos (detalle en POC-RAMAS.md, sección "Validación automática de PR").

Lo que no se ha probado es su ejecución dentro de Azure DevOps.

Por qué «Basic merge (no fast-forward)» y no las otras opciones

  • Fast-forward puro: bloquea el PR a sbx cada vez que sbx avanzó (PoC, hallazgo H2). Además, Azure DevOps no lo ofrece tal cual: su opción "Rebase and fast-forward" reescribe los commits cuando no puede avanzar directo.
  • Squash y rebase: crean commits nuevos en lugar de los originales. Entonces el commit del tag deja de formar parte del historial de sbx, y la cadena y la regla "el tag es ancestro de sbx" se rompen. (Esto se deduce de cómo funciona git; la PoC no lo ejecutó.)
  • No fast-forward con la regla de cadena: todas las corridas de la PoC dejaron los ambientes idénticos al tag (escenario 12).
